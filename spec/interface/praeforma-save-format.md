# Praeforma の保存形式

2026-09-07 の設計合意。保存方式は **OKF Markdown と構造化 JSON を別ファイルにする**。
本書は実装へ引き継ぐ設計契約であり、保存機能や変換器が実装済みであることを示さない。
具体的な JSON Schema、ファイル配置、移行処理は実装時にこの契約に沿って定義する。

## 正本と責務

| 形式 | 正本として持つ内容 |
|---|---|
| OKF Markdown | プロダクトの価値、設計意図、説明仕様、境界の理由、人間の判断理由 |
| JSON | アクター／シーンの構造、定義と配置インスタンス、参照、レイアウト、画面遷移、機械処理するパラメータ |

同じ意味のフィールドを双方の編集可能な正本にしない。JSON の構造を Markdown に表示する場合は
生成された射影として扱い、説明文から構造を変更する場合も差分付き変更提案を経由する。
対象プロダクトのリポジトリが内容を所有し、Praeforma (Pf) や Anatomia (An) の DB は別の正本を作らない。
既存の `spec/ux/product.md` と `spec/ux/<domain>.md` は
[UX 定義書](../../FORMAT_UX.md)に従い維持する。

文書と構造要素は安定 ID で関連付ける。表示名、ファイル名、配置位置の変更で ID を変えない。
定義 ID とインスタンス ID は区別し、参照には種別を持たせ、LLM が名前だけから型や所属を推定する
必要のない形にする。文書の取得・版識別は
[UX 参照読取契約](ux-reference-read-contract.md)を使用する。

## アクターとシーン

アクターとシーンは別の型とする。

- アクターは状態・振る舞い・公開パラメータを持つ設計上の主体。アクターにアクターを入れ子にできる。
- シーンは配置・表示・遷移を構成する単位。シーンにシーンを入れ子にできる。
- それぞれ独立した定義をパーツとして参照し、複数の箇所から再利用できる。
- シーンにはアクターのインスタンスを配置できる。その配置によってアクターをシーン型へ変換しない。

例として「プレイヤー」はアクターであり、コアドメインとして設計する対象にもなるが、シーンではない。
「タイトル」はシーンであり、それだけでドメインにはならない。すべてのアクターをドメインと見なす
規則も設けない。ドメインの責務・境界は独立して定義し、シーンの配置・包含・遷移から導出しない。
非コアドメインは基本的に Anatomia で管理する。

## 定義とインスタンス

再利用する定義と、呼び出し先に置くインスタンスを分ける。定義を複製して同一性を失わせない。
各インスタンスは参照先の定義 ID、自身の ID、配置および許可された公開パラメータの上書きを持つ。
上書きは定義の既定値に対して明示した値だけ適用し、別のインスタンスや元定義を変更しない。
設計用のサンプル状態と、ゲーム等の実行時セーブデータは区別する。本契約は設計成果物の保存を扱う。

アクター包含とシーン包含それぞれで循環参照を検出し、無限展開する構造を確定保存しない。
画面遷移のループは包含の循環とは異なり、通常の遷移として許容する。
参照切れ、型不一致、ID 重複は対象 ID と参照元を示す診断にし、黙って削除・別種へ変換しない。
一時的に不完全な編集案を保存する場合は、検証済みの正本と区別する。

## レイアウトと表示上の契約

- 複雑な UI はボックスとして表現できる。内部を未設計であることを説明できるようにする。
- 動的オブジェクトはサンプル表示と、動的であること・更新条件を持つ。
- 追従 UI は画面上に通常どおり配置し、追従対象の安定した参照と条件を明記する。
- スマホでの編集・確認を可能にし、表示幅に応じた条件や上書きを基礎の定義と区別する。
- 画像の LLM 解析結果は編集可能な案とし、人間の確認なしに既存の正本を上書きしない。

## 版と変換

JSON は明示したフォーマット版を持ち、その版の JSON Schema で構造を検証できるようにする。
未対応の版・未知の情報を黙って落として保存しない。移行は差分を確認できる別の変更として扱う。
複数ファイルにまたがる変更では参照整合性と対象版を確認し、途中状態を確定版として公開しない。
JSON Schema の構造検証だけで参照先の存在や包含循環まで合格と見なさない。

Figma、AI 入出力、Markdown への変換は正本からのアダプターとして設計する。
Figma 等の表現へ対応付けられない振る舞いは、サンプル表示・付随情報と変換時の欠落報告で示す。
汎用 JSON をそのまま Figma が読み込めることや、全情報の無損失往復を前提にしない。
再取り込みは安定 ID を照合する変更提案とし、参照や人間の判断を生成結果で黙って置き換えない。

読取正常と人間の承認は独立した状態とする。構造データの承認でも対象 ID、内容版、対象範囲を
明示し、関連する依存変更を検知する。LLM の確信度や Schema 検証合格を承認の代わりにしない。
対話による不足解決は [UX 価値の対話契約](../feature/ux-value-dialogue.md)に従う。

## 実装時の受け入れ観点

1. 同じアクター／シーン定義を複数配置し、一方のインスタンス変更が他方へ漏れない。
2. 各型の入れ子を再利用でき、包含の循環を診断しつつタイトルへ戻る画面遷移は保持できる。
3. シーンの移動や再編成でドメイン所属・境界が変わらない。
4. 保存・再読込で安定 ID、型、配置、上書き、動的表示と追従条件を維持できる。
5. OKF と JSON の内容所有が一意で、参照切れ・未対応版・競合を利用者が確認できる。
6. 変換で表現できない情報を報告し、再取り込みは元の設計と比較して承認できる。

初期の確認対象は Pf 上のモックとし、その結果を対象プロダクトの実装・テスト証拠へ昇格しない。
この一覧は実装時の確認観点であり、本設計変更でテストを実施したという記録ではない。
